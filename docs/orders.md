## Rules (each one was a bug or an owner decision)

1. **Only cases the owner cares about** (Kuzatuv companies, a Sud ishlari list, one drawer). No full-library crawl (laptop/disk).
2. **A published order is permanent.** An instance with a stored order is never asked again; all four (first, appeal, cassation, taftish) stored = done for good.
3. **Re-check only when it can matter:** the case signature changed (status/result — e.g. appealed), or a publication-lag back-off elapsed (3 d, 14 d, 45 d, then wait). A failed search is retried after 10 min and is **never** recorded as «none».
4. **Still heard in the first instance (no result, «ish yurituvda» / «koʻrib chiqilmoqda») ⇒ no decision ⇒ not queued.** Appeal / cassation / supervision ⇒ checked (its first-instance order exists). Unrecognised wording ⇒ checked. A hand «Tekshirish» overrides.
5. **Nothing starts by itself and nothing nags.** Opening/refreshing/switching pages or tabs never queues or scrapes. DETECT (`plan`) is free and only shows a count («Qarorlar · N», «N ta ish tekshirilishi kerak»). SCRAPE runs from a click or the opt-in idle check.
6. **The pill exists only while scraping**; ✕ hides it for that run (sessionStorage); paused/failed/finished leave no pill — one toast at the end (with «Qayta urinish»); a paused queue is continued from Kuzatuv or Settings.
7. **Pause really pauses:** state flips at once, the case in flight finishes, the queue keeps its order, resume continues with the same counters. Automatic feeders send `keepPaused` so they cannot undo a pause.
8. **The cache is never deleted by the app** (no clear button, no DELETE route). It lives outside the project; writes only append (newer line wins on read); files are `0600`, dir `0700`.
9. **One shape, one signature:** every caller builds jobs with `orderJobCase` (status + result). Two shapes ⇒ screens keep «changing» each other's cases.
10. **One status poll** (`use-orders-job.ts`); local reads (`status`, `cache`, `orders`) are exempt from the scrape rate limit, `plan/start/...` are not.
11. **Searches are slow** (≈10 s per `case_number`+`instance`, a minute+ without instance) ⇒ background only, one case at a time, 3 instance searches in parallel. Never hedge/duplicate them.
12. **A PDF may need a person («Qoʻlda yuklash»).** public.sud.uz now accepts a download only with a token from a SOLVED human challenge (`public-sud-api.md`). When every automatic route is refused, `GET /file` answers `409 manual_required` and the automatic route rests for 30 min (`ManualDownloadRequired`, no more captchas burned; `&retry=1` = the card's «Avtomatik qayta urinish»). The order card then offers: open public.sud.uz, save the PDF there, pick it → `POST /api/public-orders/import?id=<pdf id>` (raw body, up to 100 MB: `guard({maxBodyBytes})`; only a real `%PDF-` is kept, a site-wrapped multipart file is unwrapped) → stored in `files/` exactly like an automatic download, so every later click is served from disk. The id comes from the card the person picked, never from the file. Listing/search and the case database are unaffected.
13. **Every PDF the person opens is kept, forever** (`files/<pdf id>.pdf`; the file route writes it on the first download, the import route on a hand-over), and the Qarorlar page shows exactly which ones are on disk. **Deleting a saved PDF is noticed:** `files/` alone cannot say whether a file ever existed, so every save appends a line to `downloads.jsonl` (pdf id, size, time, the court's file name; newest line wins; never deleted by the app), and the page lists a file that is in the log but not on disk as **«Mavjud emas»** (its old size and date kept); a PDF already on disk when the log started gets a `seen` line the first time the page is read, so deleting THOSE is recognised too. Clicking such a row downloads it again from the stored order data (the row's `pdfId`) and the state returns to «Yuklangan». The background check stores only the small order rows, never PDFs (one captcha per PDF would turn a check into a crawl). Searching is a local read: typing never reaches public.sud.uz.
14a. **A download must really reach the server, and the server must say whether it kept the file.** `GET /file` answers `Cache-Control: private, no-store` and the client fetches with `cache: 'no-store'` (every JSON read of the app too): a browser-cached PDF used to answer a later click («Yuklab olish» / «Qayta yuklash») WITHOUT the server seeing it, so the file was never (re)saved and the order could not move to «Yuklangan». The response carries `X-Order-Saved: 1|0` (+ `X-Order-Save-Error`); the loader reports `saved` (a failed write is NOT swallowed any more: the PDF is still returned, the page says it was not kept and why). `pdf-store.writePdf` retries the rename (Windows antivirus holds a fresh file: EPERM / EBUSY), falls back to a copy, and verifies the size. On the Qarorlar page, **«Barchasini yuklash (N)»** (Yuklanmagan view; «Barchasini qayta yuklash» in Mavjud emas) collects the orders of the current filters across ALL pages, downloads them one by one, re-reads the lists and counts after each, stops at the first order that needs a person or the first file the server could not keep, and has «Toʻxtatish».
14. **Two back ends.** Every check asks the library (after 2024, 4 instance searches) AND the pre-2024 back end (one `caseNumber` search; `searchLegacyCase`), because one case may have orders in both. Pre-2024 orders get ids `old-<type>-<n>` (stored like any order; `isOrderFileId`/`orderFilePath` accept only that shape). **Criminal** is never crawled and has no company link: the person types a case number on the Qarorlar page (the «public.sud.uz dan qidirish» box, court picked from the number's first digit) and only that case is looked up. Criminal PDFs are scans (no text layer) and name defendants: keep it lookup-by-number.
15. **Metadata has a protected second copy** (`lib/public-orders/meta-backup.ts`, scheduled by `meta-backup-runner.ts`). The order index (`shards/*.jsonl`), the check records and the download log are mirrored to the OS app-data folder (Windows `%LOCALAPPDATA%\SudTizimi\orders-backup`, macOS `~/Library/Application Support/SudTizimi/…`, Linux `~/.local/share/sud-tizimi/…`; `PUBLIC_ORDERS_BACKUP_DIR` overrides, `off` disables; with `PUBLIC_ORDERS_DIR` set there is no backup unless that variable is given): `latest/` ≈ 15 s after any write, plus `daily/<date>/` (7 kept). The mirror never deletes and never replaces a file with a smaller one (the files are append-only: smaller = damaged). At the first use of the data folder, a metadata file that is **missing or empty is restored** from `latest/`; existing files are never overwritten. So deleting `~/.sud-tizimi/public-orders` by accident loses only the PDFs, which then show «Mavjud emas» and re-download. The PDFs are not copied. To really wipe the cache, delete both folders (Settings › Qarorlar shows both paths).
16. PDFs are anonymised, rows carry no parties/STIR; only look up cases the owner opened/watches.

## Flow

```
drawer «Tekshirish» ─► POST /fetch {start,cases}   (the Kuzatuv / list bulk checks and the idle auto-check were removed)
                                              planCases (planCheck + ongoing filter)
                                              └─► queue ─► loop: lookupCase ─► source ─► store
a person-saved HAR / PDF ─► POST /import-har | /import ─► files/ + shards (the way new orders come in while the site refuses scripts)
```

## Hand-over by HAR (how an order gets in while the site refuses scripts)

For the person, step by step (the same text is in the app: `HarHowTo` in `proto/order-handover.tsx`):

1. In YOUR browser open public.sud.uz, press **F12** › **Network** (keep it open), then search the case again (the search answer must be in the log too: it carries the case number, court and instance) and open the order.
2. Network toolbar › **Export HAR (sanitized)**. If the importer says the file has no contents, export **with sensitive data** instead (older Chrome: «Save all as HAR with content»).
3. Qarorlar › **HAR fayldan yuklash** › pick that one file.

What the importer does (`lib/public-orders/har-import`, `POST /import-har`): reads ONLY each entry's URL path and response body; stores every order file under the id in its own path, and adds the order RECORDS from the browser's own search answers in the same file, so each file lands on a card. It never reads cookies, tokens or headers and sends no request to any site; the file itself is local and not kept (`*.har` is in `.gitignore`). **A HAR of search pages only** (orders found, no file opened) is accepted: its records are stored and the orders appear as «Yuklanmagan»; only a HAR with neither a file nor a record is refused (`no_order_file`). **An order the person cleared («Tozalash») and hands over again comes back to the lists** (`hidden-store` restore; the answer's `restored`). **Overlapping exports are safe:** inside one HAR the same id is kept once (the bigger copy); against the disk, a file whose id is already stored with the same size is NOT written again (no rewrite, no new download-log line, no new «saved at»), and an order record identical to the stored one is not appended again. The answer counts `saved` (new files), `skipped` (already here) and `orders` (new or changed records), and the page says «Yangi qaror yoʻq: N ta fayl allaqachon bor» when nothing was new. So a log kept over pages 1-5 and then 6-10, or the same file twice, only adds the difference. Limits: 256 MB per file, at most 500 order files per HAR (`MAX_HAR_FILES`); Next's own body cap is raised to 300 MB in `next.config.ts` (`proxyClientMaxBodySize`, tested in `server/__tests__/body-limit.test.ts`: the default 10 MB cut a body silently).
A file with no matching record is reported to the person and in dev.log (`[orders-har]`).

**Tozalash:** in «Yuklanmagan» / «Mavjud emas» tick orders to download them, clear the ticked, or clear the rest. Cleared ids sit in `hidden.json` (`hidden-store`); the order records stay. A search finds a cleared order again (badge «Tozalangan», «Qaytarish», «Yuklab olish»); a DOWNLOADED order can be cleared too («Oʻchirish» on its row, or tick several in «Yuklangan»): only the row and the counts go; its record AND the PDF stay (nothing is deleted from disk), and from the «Tozalangan» view «Ochish» opens the saved file in one click, «Qaytarish» puts it back.

## PDF downloads: «previous done + a short rest», not a fixed 10 s (Nov 2026)
Searches keep the start-to-start gap (`ordersPace`, 10 s). PDF downloads use `lib/net/serial-gate` through `pace.ordersFileSlot`: ONE download at a time (a gate held from the file request until its body is read, released on success AND failure), and the next one may start `PUBLIC_ORDERS_FILE_GAP_MS` (default 4 s, `0` = no rest, capped at 120 s) after the previous one FINISHED. Why: the old rule held every file to a start-to-start 10 s even when the previous download had already used most of it (a captcha and a download take several seconds on their own); counting the rest from the END means a slow download is followed by just the short rest, a quick one by the same short rest, and two requests are never in flight together. A person's own PDF no longer waits behind a crawl's 10 s slots, but it still queues behind a running download. The firewall's circuit breaker (`lib/public-orders/waf`: the first block pauses all direct requests for 15 min) is unchanged and checked before and after the wait. The real rate is bounded by the captcha (`getCaptchaToken` runs one session at a time in `pdf-load`), so the gain is the part of the old 10 s that the captcha did not already fill. If the firewall ever blocks downloads again, raise `PUBLIC_ORDERS_FILE_GAP_MS` (e.g. 10000 restores about the old behaviour). Tests: `net/__tests__/serial-gate.test.ts`, `public-orders/__tests__/pace.test.ts`.

## «Barchasini yuklash» is a server job; what it skips, and removing orders that can never be downloaded (Nov 2026)
**Server job** (`lib/public-orders/download-job` (pure) + `download-job-real` (the instance on `globalThis`), `GET|POST /api/public-orders/download-job`, `hooks/use-download-job`). It used to be a loop inside the Qarorlar page, so leaving the page stopped it. Now the page only starts it (`{action:'start', ids}`; ticked ones, the whole view across pages, or the search result) and WATCHES it (polled every 2 s while it runs), so any navigation, a closed tab, a company card or the stats page does not touch it; the page, when opened again, finds it running or its report waiting («Yopish» dismisses it). One job at a time; it uses the shared `loadOrderPdf` (one captcha session at a time, the pause after a refusal) and the PDF gate (`ordersFileSlot`), exactly like a click or the bot's «Yuklash»; `/api/presence` counts it as busy so Sud.bat does not stop under it. «Toʻxtatish» stops after the order in flight. Nothing starts by itself.
**What it does with an order that cannot be saved: skip it, and tell at the end** (no more «stop at the first problem»): **«public.sud.uz bu qarorni qoʻlda yuklashni talab qildi»** → that order is listed with the way out (open it in the browser, hand it over with the HAR import) and SKIPPED; the loader now rests for 30 minutes, so the next order is a PROBE (`retryAuto` reopens the rest, at most three captcha sessions): one refused order does not end the list (a first version stopped after ONE refusal and left 227 orders untried). Only when the site refuses `MAX_REFUSED_IN_A_ROW` (3) orders in a row is it closed for now: the rest is NOT tried (`deferred`, no more captchas burnt) and the job ends; press again later, only what is still not downloaded goes on. **«Fayl PDF emas»** → asked once more; if the second answer is not a PDF either, the order is **removed from the metadata** and listed as removed. **Any other failure** (a timeout, a 5xx) → listed with its reason and skipped. **A file that arrived but could not be kept on disk** → the job stops and says why (systematic).
**Removed orders** (`lib/public-orders/purged-store`): an append-only `purged.jsonl` (`{pdfId, caseNumber, at}`) next to the shards (mirrored by `meta-backup` like the other metadata files). The shard lines are never rewritten (the store is append-only): every reader leaves out a record whose file id is listed (`allOrders`, `lookupOrders`, so the Qarorlar lists, the counts, the case drawer, the backup, the restore). A re-check of the case that finds the same order again appends it again, and it stays hidden. The backup carries a **tombstone line** `["x", pdf id, when, case number]` in the `orders:<yy>` bucket: `mergeBucketText` drops every order with that file id from the union (so the channel's older copy cannot bring it back), `importOrdersBucket` records the tombstone on a restored computer and skips the order, and the bot's `orders::parse` leaves it out of every list. **Treat removal as final:** the tombstone, once in a channel's bucket, stays there (a union never deletes), so deleting the line from `purged.jsonl` brings the order back on this computer only until the next backup merges the channel's copy. Tests: `public-orders/__tests__/download-job.test.ts`, `lib/__tests__/backup.test.ts` (tombstone), `bot/src/tests.rs` › `a_tombstone_removes_the_order_from_every_list`.

## Routes for a PDF download: rotation, resting routes, and failures that repeat (Nov 2026)
A download is a captcha session plus the file request, and both run on ONE route (the token may be tied to who asked): **this machine** (its own IP) or one of the Cloudflare workers (`order-file`). Field log: this machine could not reach the captcha host (3 × 10 s of timeouts for EVERY order), the token was then minted through a worker, and the worker answered `403 «Host adolatapi1.sud.uz not allowed»`: that worker had been deployed before the repository's `cloudflare-worker/proxy.js` allowed the host (the repository's list has it; the DEPLOYED copies must be updated by pasting the file in Cloudflare › the worker › Edit code › Deploy, for each worker). So:
- **A route that fails for a reason that repeats rests** (`createRouteHealth`, one per server on `globalThis`): no token (the captcha host times out) 10 min, a network error on the download 5 min, «Host … not allowed» (an old worker) 60 min, with the reason kept; the next orders skip it without spending 30 s or a captcha, the order is served by the next route, and a success clears the rest. A token REFUSED by the site is not a route failure (it is the site wanting a person: `CaptchaRefusedError` as before). When no route worked and none was a refusal, the error is `RoutesFailedError` and says every route's reason («hech bir yoʻl ishlamadi · …»).
- **Round robin** (default): each download starts on the next route (this machine, worker 1, worker 2, …) instead of always this machine first, so the load and the IP the site sees are spread; `PUBLIC_ORDERS_ROUTES=direct` restores «this machine first, always». The workers' addresses are Cloudflare's, shared with other users of the platform and not a private pool, and each route is still held to the one-at-a-time gate (`ordersFileSlot`), so rotation spreads the IP, it does not raise the rate.
- **The bulk job says a repeated failure once** (`MAX_SAME_FAILURE_IN_A_ROW`, 3): the same message for three orders in a row is not about the orders, so the rest is left (`deferred`) and the reason is shown once at the top of the report instead of 200 identical lines. Different failures in between reset the count.
Tests: `public-orders/__tests__/{order-file,download-job}.test.ts`.

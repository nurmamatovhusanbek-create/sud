### Change the Statistika pie («radial stack»)

### Counting numbers, copyable identifiers, receipts from a court the case API lacks
- **`CountUp` retargets from what is on screen.** Invoices stream in one by one (target 1, 2, 3, 4, 5 while a count is running). ## 📄 DOCUMENTS — the `.docx` engine

### Add/edit a form-driven document (visa, IIO, court)

**Where:** `src/lib/documents/registry.ts`

Declares each document (id, template, fields) and each category (label, shared field groups). The editor, its live preview and the download all pick a new document up automatically — every field in `fields` must have a `{{key}}` in the template (and vice versa), or the form and the page disagree. Give fields a `placeholder`: it is what an empty spot shows on the page.

### Change how templates are filled

**Where:** `src/lib/documents/fill.shared.ts` (the substitution) · `fill.server.ts` (download: reads template, swaps letterhead, zips)

Trivial `{{key}}` string replace inside `word/document.xml` via JSZip. **The substitution is isomorphic on purpose:** the server download and the browser live preview both call `fillXml`/`markXml` from `fill.shared.ts`, so the preview can never drift from the file. Change fill behaviour there, never in only one side.

### Change the document editor (form ↔ live page)

**Where:** `src/components/views/doc-editor.tsx` (form, sections, doc switcher, downloads) + `src/components/proto/doc-preview.tsx` (live render) + `.dedit*` / `.dprev*` in `prototype.css`

Split view: fields left, the REAL .docx template rendered right (via `docx-preview`), filled as you type. Click a value on the page → its field focuses; focus a field → its spots highlight. Combined categories (visa, iio) share one form and get a doc switcher + «Barchasi»; court docs get one doc with sectioned fields (`sectionsFor` in the registry).

### Change how the preview is drawn

**Where:** `doc-preview.tsx`

Pipeline per change (debounced): template zip → `markXml` wraps each value in private-use sentinels (U+E000–E002) → letterhead swap → `docx-preview` renders **off-screen** → sentinels become `<span class="slot" data-k>` → DOM swapped in (no flicker, scroll kept). Empty spots show the field's example text (`placeholder`) in italics; the real download still leaves them blank. Slot tints are fixed light colors because the paper is always white, even in dark mode.

### Fill one document for many rows («Jadvaldan»), PDF, ZIP

**Where:** `views/doc-bulk.tsx` · `lib/documents/bulk.ts` (read csv/xlsx, match columns by field label or key, rows → values; pure) · `bulk.server.ts` + `api/documents/generate-bulk` (one .docx per row, numbered, one zip, max 300 rows) · `lib/xlsx-grid.ts` (the minimal xlsx reader, shared with `pretenzia/parse.ts`)

Each row is laid over the form's values (what is shared is typed once) and checked with the same `validate.ts` checks; nothing blocks. **PDF** = `print-render.ts`: the same `fillXml` as the download, rendered by docx-preview off-screen and printed by the browser (the window is opened inside the click). **«Barchasi · ZIP»** zips a combined category's documents client-side. Drafts / saved profiles / checks: `drafts.ts`, `profiles.ts`, `validate.ts` (all pure, storage injected).

### Write a document in the new Latin alphabet (2026) or Cyrillic: «Yozuv» switch

**Rule:** the new alphabet changes exactly four letters, both ways: `Gʻ gʻ → Ğ ğ`, `Oʻ oʻ → Ö ö`, `Sh sh → Ş ş`, `Ch ch → Ç ç`. The other 24 letters and the tutuq belgisi (`ʼ`, a separator) are unchanged. Everything in the app and in the templates is written in the OLD alphabet; the choice (old / new, remembered in the browser: `lib/documents/script-pref`, key `sud-doc-script`) is sent with each request and the server remembers nothing.

**Where:** `core/uz-alphabet.ts` (the ONE converter: pure, returns `Edit[]` so the docx step can map them onto Word runs; never write a second one, never `.replace(/sh/…)` in a component) · `lib/documents/script.ts` (`convertWordXml`, `applyScriptToZip`, `valuesForScript`, `resolveScript`) · wired into `fill.server` (download + ZIP + spreadsheet), `print-render` (PDF), `proto/doc-preview` (live page), `pretenzia/fill.server` (Uzbek talabnoma only) and the three routes (`script` in the body, `parseScript`). UI: the `Yozuv` control in `views/doc-editor` and `views/pretenzia-view`. Tests: `core/__tests__/uz-alphabet` (the alphabet chart, fuzz), `lib/documents/__tests__/script` (every shipped template, every document end to end), `lib/pretenzia/__tests__/script`, `core/__tests__/translit`.

**Why it is built this way (each one was a bug found by a test):**
- **Word splits words across runs** (`Oʻ`+`zbekiston`, `O`+`’`+`zbekiston`, `S`+`h`), and templates spell the modifier several ways (`ʻ ‘ ’`). So a paragraph's runs are ONE text stream; an edit lands in the run of its first character and the consumed characters leave the others. Paragraph ends, line breaks, tabs, pictures and field characters are boundaries. Only the text inside `<w:t>` changes; every tag/attribute/untouched run stays byte for byte.
- **`{{placeholders}}` are opaque** (a key such as `{{short_name}}` must never be converted) and the template and the values are converted in two separate steps. In the preview the markers are added AFTER, so the field keys inside them are safe.
- **Typed text is first normalised to the old alphabet**, then derived (Cyrillic names, initials, dates), then converted once; so a name typed `Şuhrat` gives the same Cyrillic as `Shuhrat`, and `core/translit` only ever sees one spelling. `с`+`ҳ` (Исҳоқ) keeps a tutuq (`Isʼhoq`) so it is not read as the digraph `ш`.
- **Not Uzbek words are never touched:** e-mail, links, domains, codes (`SH123`, `AA1234567`) and numbers like `SH-12/2026` / `PF-5712`; `5-chi` and `Oʻzbekiston-2030` ARE words. English documents (declared `lang: 'en'`, or text that reads as English: the operator's own templates) get NO conversion in either direction (`should`/`which`/`Chief`, a Turkish surname such as `Özdemir`).
- **New → old:** a plain `s`+`h` in a token that already has a new letter is two letters and gets the tutuq (`Öshoq → Oʻsʼhoq`). A digraph is upper-case in an upper-case word (`ŞARTNOMA → SHARTNOMA`), and title-case for initials (`Ş.A. → Sh.A.`).

**Cyrillic («Кирилл»).** Third choice of the same switch, shown only for a document with `DocDef.cyrillic` (the four court petitions `court_*`) and for the Uzbek talabnoma (`pretenzia/fill.server`, `lang === 'uz'`; the Russian talabnoma and every other document ignore it, and a saved «cyr» shows as the old alphabet there: `effectiveScript`). **Interpretation:** «talabnoma group» = the Talabnoma section (`talabnoma-uz.docx`); `visa3_talabnoma` and `iio2_royxat` carry the word in their names but belong to the visa / IIO groups, so they have NO Cyrillic version; one flag per document turns it on if the owner wants them. Same machinery as the alphabet change: `editsToCyr` in `core/uz-alphabet` (edits, so the docx step maps them onto Word runs), same protected tokens, English untouched, values typed in any script are normalised to the old alphabet first. Rules that are not a letter table: `oʻ gʻ sh ch → ў ғ ш ч` (any capitalisation); `yoʻq` is `й+ў+қ`, not `ёʻқ`; `ya yo yu ye → я ё ю е`; `e` is `э` at the start of a word and after a vowel, `е` after a consonant; the tutuq is `ъ` between letters and `ʼ` between `s` and `h` only says «two letters» (`Isʼhoq → Исҳоқ`); `ts → ц` between vowels / at the start (`federatsiya`, `Tsentr`); loan-word prefixes `ob sub pod pred raz iz in kon ad` + `y` + vowel get the `ъ` the Latin spelling leaves out (`subyekt → субъект`); a token with a letter that has no Cyrillic (`c` outside `ch`, `w`) is a brand and stays whole (`Wi-Fi`, `Coca-Cola`). A suffix on a number (`10:00ga`, `5ta`) and on a code (`SH-12/2026-sonli`) IS converted (`CODE_CYR`, `CODE_TAIL`). Tests read it back with the app's own reverse converter (`translit.uzCyrToLat`): hand-picked words, a fuzz, every Cyrillic template paragraph. **Known limits:** `ts` between two vowels is always `ц` (`otsa` would read `оца`); `-tsiya` words are spelled `ц` in Cyrillic, but Latin `inyeksiya` has `ks` (`инъексия`); Russian-spelling names (`Ю`, `Щ`, `Ы`, `Ь`) are not produced.

**Known limits (documented in the tests, not hidden):** one capital `Ş`/`Ç` cannot remember whether it was `Sh` or `SH` when it is alone or in an initials token (`SH.` comes back `Sh.`, a bare `CH` word comes back `Ch`); a name typed in the new alphabet with no marker letter in its token (`Ishoq`) is read as the old digraph. **Decision to confirm with the owner:** abbreviations follow the letter rule, so `MChJ` becomes `MÇJ`; a legal-entity name quoted from a register may need to stay as registered.

### Which side is the company on (plaintiff / defendant)

**One definition:** `assignRoles()` in `core/classify.ts`, used by BOTH `lib/stats.ts` (side → win/lose/neutral, classified AFTER all courts are pooled) and the Sud ishlari filter «Ikkala tomon · Daʼvogar · Javobgar · Noaniq» (`sections/cases.tsx`, `sideOf`, computed over the whole loaded list, not the search results). **Why not name matching:** (1) `nameMatches()` matches any two MChJs (the expansion «mas'uliyati cheklangan jamiyati» alone is ≥ 2 shared words); (2) the courts write Cyrillic («ПРОКАБ» МЧЖ), the registers Latin (PROCAB MChJ), and the spelling differs beyond script (c/k, q/k, x/h, b/p…), so the company did not match itself (field report: out of 100 cases 0 plaintiff, 3 defendant). **How it decides:** every case was found by the company's TIN, so the company is a party of nearly every case: its spelling is the one name present in ≥ 60 % of the cases (and ≥ 2) — LEARNED from the list, script- and spelling-proof (`partyTokens`: Cyrillic→Latin, legal-form words dropped, vowel-less folded skeleton). Order of trust per case: a 9-digit TIN in the party text → the learned name → the known company names (only as a tie-break between unrelated recurring names, or when nothing could be learned) → unknown. Spellings of one name («PROCAB» / «PROCAB GROUP») count as the same company; the company on BOTH sides, or on neither, is unknown. **Never guessed:** `null` = «Noaniq» (the chip appears only when > 0, so the three counts add up to the list); stats keeps the old default (plaintiff) for the win/lose maths. Only the 40 most frequent exact names are scored against the list (keeps it O(cases × 50), ~165 ms at 1500 cases). The filter also narrows PDF print and the «Qarorlar» check (not the Excel export, which is server-side by STIR). Tested in `core/__tests__/classify.test.ts` (100-case Cyrillic scenario, recurring counterparty, ties, blanks); a 20-run random simulation (typos, blanks, third parties) gave 0 wrong sides.

### Worker health history (Settings → Holat: Bugun / 7 kun / 30 kun / Barcha)

**Bug fixed:** the history lived only in the pool's memory (a 500-record ring per origin × worker): every server restart (the dev supervisor restarts on crash and HMR rebuilds re-created the pool) emptied it, and a busy worker pushed older requests out, so the long spans could never reach back. **Now:** `OriginHealthPool.pushHistory` also calls `recordRequest` (`lib/health-store.ts`): per worker × origin it keeps COUNTS per hour (ok · fail · summed ms) for 35 days, rolled up into per-day counts after that and kept (≈ 40 bytes a day, so «Barcha» is all time), plus the last 300 raw records for the drawer and the bars. ## Daily snapshots (`lib/snapshot-store`)

A company used to be scraped again whenever the 5 min browser cache or the 60 s / 10 min server memory had lapsed, and
every server restart emptied the server ones. Now `stats`, `company-info` and the court lists (`mode=tin`) go through
`viaSnapshot` in their routes: a part younger than 24 h is read from `~/.sud-tizimi/snapshots/<STIR>.json` and no site is
touched; older (or missing) is scraped and replaces it; `force=1` (the hard refresh) scrapes regardless. Upcoming hearings
are deliberately not a part: they stay live (5 min).
Rules: only COMPLETE answers are stored (`storable`: stats without court errors and with a found company, info without
`partial`, a court list that is not `incomplete`); a failed refresh keeps the old snapshot; a plain open whose re-scrape
fails serves the expired one flagged `stale` (meta `stale`); a forced stats scrape drops that company's `court:` parts
(the lists must not be older than the stats beside them); `force` also drops orginfo's 24 h memory (`forgetCompany`), or
the «fresh» answer would be the old one. The STIR is the file name, so exactly 9 digits. Files and parts unrefreshed
for 7 days are deleted (hourly sweep, mtime). Responses carry `meta.fetchedAt` / `meta.cached` / `meta.stale`.
Tests: `lib/__tests__/snapshot-store`, `lib/__tests__/snapshot-routes`.

### Hard refresh and the age label

The header's circle button and the R key run `hardRefreshWithToast`: forced stats (which refills the server's court-list /
orginfo memory and, when complete, retires the older info / court / bills snapshots), then the live hearings, then the event
`sud:company-refreshed`, on which the active section re-reads (`reload()`: no second scrape). The toast says how it went:
«Yangilandi» · «…lekin majlislarni olib boʻlmadi» · «Yangilab boʻlmadi … eski maʼlumot qoldi» (an incomplete stats answer is a
failed refresh: nothing is stored and the registry meta keeps its numbers). Stats, company info and court lists use
`useResource({ persist:false })`: the server's snapshot is the only copy, so there is nothing in the browser to hide a refresh
done elsewhere. Sections report `meta.fetchedAt` to `lib/data-age`; the header shows «Yangilandi 3 soat oldin» (the OLDEST part;
the tooltip lists each; «· eskirgan» when the sites failed and a past-day snapshot is shown).

### Bills in the snapshot

`/api/bills?inn=` replays a fresh stored list as the SAME NDJSON stream (meta · bills · done; `meta.cached`, `meta.fetchedAt`,
`done.fetchedAt`), so there is no captcha and no scrape inside the day; `&force=1` always scrapes. A live scrape is stored
(`lib/bills-snapshot`, the final list after the retry round) only when no bill is left with a TRANSIENT error (a definitive
HTTP 4xx/5xx for one receipt is a stable fact and does not block it). If the live scrape fails before anything was sent and an
older snapshot exists, that is replayed with `stale:true`. A forced, complete stats scrape retires the bills snapshot, so the
header's hard refresh makes the next Bills open (or the open one, immediately) scrape. Removing a company in the app calls
`DELETE /api/snapshot?tin=` and its file goes. Tests: `lib/__tests__/bills-snapshot`, `snapshot-routes`.

**Waiting for an update to finish (`lib/update-wait.ts`).** An update restarts the server, and often TWICE: `git pull` changes a file Next watches (`next.config.ts`) so the dev server restarts itself, then the supervisor cycles it again after `bun install` (the sentinel is deleted within a second, so it is no signal). A request in flight during either restart is cut off. So the Updates tab never treats a cut connection as a failure, and never treats «something answered» as done: it waits for a server whose **commit moved**, whose **start time is new** (`GET /api/settings/version` → `local.bootedAt`) and which keeps answering from that one process for four polls in a row; if nothing changes for ~9 s it concludes the request really failed («Tarmoq xatosi»). The first update that carries this fix still runs the OLD screen once; every later one uses it.

## Koʻrinish uslublari (Premium / Moviy)

Two looks, chosen in Settings › Koʻrinish (default «Premium»). Mechanism: `lib/look` + `LOOK_BOOT_SCRIPT` put `data-look` on `<html>` before paint; `app/look-premium.css` re-points the tokens (light and dark) and restyles under `[data-look='premium']`; the markup is shared with «Moviy».

**History, so it is not repeated.** «Tinch» (graphite, hairlines) was judged flat and tiring. Attempt 1, «Yorqin» (six rotating pastel hues on tiles, chips and monograms): *a mess; more colours is not a premium look and gives no identity*. Attempt 2 (serif titles, ivory canvas, brass accent, ornament): *not our font; it reads as a product or beauty site, and we are a legal/registry tool*. «Premium» is the third approach: identity from precision, not decoration.

- **Materials: two colours.** Ink `#111114` (sidebar, primary buttons, monograms) and near-white (white surfaces `#FFFFFF` on a faintly grey canvas `#F4F4F5`, never a pure-white page). **No blue and no accent hue, in either theme** (owner, Nov 2026: «two colors seems fine, no need for dark blue on both themes»): selection, links, focus rings, tab underlines and the sidebar marker are ink (white in dark mode); the tile icon gradient runs graphite to ink (light) or light to mid graphite (dark). **SQLite (Nov 2026): what it is and the rules.** One file, `~/.sud-tizimi/sud.db` (`SUD_DB` overrides), holds the bills of every company (`bills`, one row per (tin, number); `bill_loads` = pass state), the cases found by number from the bills (`found_cases`, keyed (court, tin, num) so the list is paged and filtered in SQL), the numbers already asked (`tried`), the full cases (`case_details`, gz JSON blob, never expires) and `meta`. ## Telegram backup (Nov 2026)

The database can be kept, encrypted, in the operator's own Telegram channel (Settings › Telegram). `lib/backup` (job), `lib/backup-crypto` (pure crypto), `lib/db-buckets` (the cutting), `lib/telegram-client` (Bot API, ONE fixed host).
**Incremental and content-addressed (manifest v2).** A consistent snapshot (`VACUUM INTO` a temp file) is cut into BUCKETS: a company's bills of one year (`bills:<tin>:<year>`), its found cases by court and year, case details by court and registration year (`case_details.yymm` is a generated column, migration v3), tried numbers, and a small state bucket (load state + the two dates). A bucket is deterministic text (rows in key order; the bills' `pass` counter is left out because it moves on every refresh), and its id is an HMAC-SHA-256 of that text under a key derived from the passphrase (not a plain hash: a guessed content cannot be confirmed without the key). The pinned manifest of the previous backup says which ids are already in the channel: an unchanged bucket is not sent again (its pieces are checked with `getFile`; one that was deleted from the channel is sent again), a new or changed one is gzipped, cut into 19 MiB pieces (a bot reads back at most 20 MB), sealed with AES-256-GCM (authenticated data `bucket:<id>:<part>`) and sent under an OPAQUE file name (`sud-<12 hex>-<n>.bin`; bucket names, tins and years exist only inside the sealed manifest). The sealed manifest lists every bucket with its pieces, each company's `firstAt`/`refreshedAt`, and a pointer to the manifest before it, and is PINNED, so a new machine needs only the bot token, the channel and the passphrase. **Nothing is ever deleted from the channel** (no «Delete messages» right needed): old manifests are history, and an unchanged bucket costs nothing. The SAME passphrase must be used every time (the salt of the chain is carried over so earlier pieces still open; another passphrase is refused). One company's refresh changes only its few current buckets (this year's bills, its found cases, details of the year, its state).
**Restore** writes a NEW file `sud.restored-<time>.db` beside the live database (opened and migrated like the live one, filled with `importBucket`, every piece checked against its hash, its tag and its recomputed bucket id, `quick_check`, the write-ahead log folded in so it is ONE file); the live database is never touched, and the operator closes the app and swaps the file. Manifest v1 (the first full-file format) still restores. The passphrase is never stored (a lost one means a lost backup). Measured on the ANOR BANK data (139 087 bills) with the v1 format: 80 MB database → 11 MB in the channel.
**Loading single companies from the channel (no file swap).** Settings › Telegram › «Kanaldagi kompaniyalar» opens the sealed manifest (passphrase) and lists what it holds (`lib/telegram-catalog`: tin, first-scrape and «as of» dates, bill and found-case counts; saved locally in `meta.telegram_catalog` after every backup and every read, never the data). «Tanlanganlarni yuklash» (`POST /api/settings/backup/load`) downloads the chosen companies' buckets plus the case-detail buckets of the court/year pairs their found cases fall in and `importBucket`s them into the LIVE database: cases and tried numbers are replaced only by newer rows (`t`), the state keeps the earlier first date and the later «as of», and when the database already holds a NEWER copy of the company (`refreshed_at` later than the backup's) its bills are only added to (`INSERT OR IGNORE`), never overwritten; other companies are untouched; refused while the bills job runs. The cached bills summary is dropped. **Before scraping:** `GET /api/bills/query` answers `inTelegram` when nothing is stored and the local catalog has the company; the Toʻlovlar tab then does NOT start its automatic load but shows «Bu kompaniya Telegram zaxirasida bor» with «Telegramdan yuklash» (passphrase typed there, not kept) and «Saytdan oʻqish». A copy loaded from a partial backup stays «not complete», so the tab resumes it like any unfinished load. Only manifest v2 supports this.
**The locator: search the Telegram copy without loading a company.** Every backup carries one `index:<tin>` bucket per company (`lib/db-buckets`): every case number with its court and registration year (found ones exactly, the ones only a bill names by the number's own first digit), every bill number with its issue year and the case it names. «Kanaldagi kompaniyalar» (the catalog read) opens the manifest and downloads only the index buckets whose id changed into the local `locator` table (migration v4; `locator_shards` remembers each company's bucket id; `lib/telegram-index`). The search box in Settings › Telegram (`GET /api/settings/backup/search`, 3+ characters, prefix on case number / bill number / STIR) reads that table only: no Telegram, no site, 10-20 ms on 210 140 rows (ANOR BANK). A hit says the company's court/year bucket and whether its data is already local (`loaded`); otherwise it can be ticked and loaded. Index buckets are never imported into a database (restore and load skip them). A backup made before the locator existed has none: the next backup adds it. A new machine needs only the bot token, the channel and the passphrase: catalog + index took 3 s for ANOR BANK.
Not done on purpose: scheduled backups (nothing starts by itself), swapping the restored file from inside the app, a bot that answers questions (planned: a standalone Rust bot that reads these buckets and keeps the locator in memory). Telegram's terms discourage using channels as general cloud storage: keep this for a modest personal backup and keep Settings › Baza › download as the other copy. Tests: `SUD_BACKUP_CHUNK` shrinks the piece size, `SUD_BACKUP_GAP_MS` (default 1100 ms between sends, Telegram allows about one message a second to a chat) sets the pause.

## Company dates: first scrape and «as of» (Nov 2026)

`companies` (migration v2, `lib/company-meta`): `first_at` = when the FIRST scrape of the company began (set once, never moved), `refreshed_at` = when the last COMPLETE bills load began (the data is as of then; a load stopped half way does not count and a resumed load keeps the date it began on), `last_added` = bills that load added. Data stored before v2 takes both from its bills load. The Toʻlovlar panel shows them and «Toʻlovlarni yangilash» (`load=refresh`) re-reads the bills; nothing refreshes by itself because the sites block bursts. Whether billing.sud.uz can filter by date (so a refresh could ask only for newer bills) is NOT known: its paging is unstable and sort is ignored, so today a refresh re-reads every page; the stored rows are updated in place and nothing is lost. A closed case older than 183 days stays frozen (`core/case-freeze`); an open one is refreshed per case by «Yangilash».

## Telegram bot (Rust, `bot/`) (Nov 2026)

A separate crate (`bot/`, axum + reqwest(rustls) + aes-gcm/scrypt/hmac, no SQLite) that reads the encrypted backup in the operator's channel and answers from memory; the app does not depend on it. It speaks the backup format of `src/lib/backup-crypto.ts` byte for byte (a Rust test opens a fixture written by the TypeScript code: `bun bot/tests/make-fixture.ts`). **Boot:** the HTTP port opens at once (Render's health check); in the background it reads the pinned manifest (`getChat.pinned_message`), derives the key (scrypt, ~1 s), downloads the `index:<tin>` buckets and builds the locator in memory (ANOR BANK: 210 140 rows, ~10 s cold, searches in ~3 ms), then checks the pinned manifest every `REFRESH_SECS` (300) and downloads only index buckets whose id changed. **On demand:** a case's detail, its found row and its bills (registration year ±1) and a bill's row are fetched from their buckets (`details:`, `found:`, `bills:`), hash-checked, opened, cached (120 MB cap); first call ~1 s, cached ~80 ms. **Chat:** a webhook (`POST /tg/<WEBHOOK_SECRET>`, also checks Telegram's secret-token header) with `/find /case /bill /company /app /status`, plain text = search, inline buttons open a case, bill or company; only `ALLOWED_USER_IDS` are answered, anyone else is told their own id (the owner reads it and adds it). **Mini App:** `GET /app` is one static page with NO external script (Telegram passes the signed launch data in the URL fragment, `tgWebAppData`, which the page sends as `x-init-data`); `/api/search|case|bill|company` validate it (HMAC-SHA-256 with the key derived from the bot token, max age 24 h) and the user id. The menu button of the bot opens it. **Host:** Docker (`bot/Dockerfile`, context `bot`), Render free web service, kept awake by an UptimeRobot ping on `/health` every 5 minutes (free tier: 512 MB, the disk is wiped on every restart, so every cold start reads the backup again). Trade-off that was accepted: `SUD_PASSPHRASE` lives on the host, so the host can read the decrypted data in memory; Telegram can read what the bot sends to a chat. Setting a webhook stops `getUpdates`, so the app's «Kanalni topish» no longer works while the webhook is set (a known channel id is unaffected).
**Bot architecture (fourth pass) and Mini App (latest).** The crate is layered, each layer knows only the one below: `telegram` (the wire: `Tg`, plus `Source` = where backup files come from and `Outbox` = where replies go, each with an in-memory variant for tests) → `backup` (open the pinned manifest, fetch/verify/open one bucket, the bucket cache) → `state` (`Shared`: settings, opened manifest, locator, cache, per-bucket download gate, rate limiter; `sync` downloads only index buckets whose id changed and drops companies that left the backup) → `service` (typed answers: `Company`, `Overview`, `CaseView`, `BillPage`, search hits; no HTTP, no chat) → the two front doors `http/` (router; `AuthUser` extractor = Telegram's signed launch data + the allowed list + the per-person limit, so a handler that takes it IS authenticated; `assets`; `webhook`) and `chat` (commands and buttons through `Outbox`); `sync.rs` keeps the locator fresh with backoff (the period doubles per failed sync up to 30 min; the bot keeps answering from what it has and `/status` says so). One error type (`AppError`: status + a sentence, body always `{ok:false,error}`). `domain.rs` structs ARE the API schema (camelCase), so a renamed field is a compile error. `testkit` builds a whole sealed backup (manifest v2 + buckets) in a `MemoryChannel`; `tests.rs` covers sync (unchanged pin downloads nothing), search, overview, case/bill/company answers, the router (401 without launch data, 403 off the list, 429 over the limit, 404 for `..` paths, the webhook's two secrets) and chat handlers; two tests guard `static/` (no `innerHTML`, no inline style, no external URL, Latin only). `RATE_PER_MINUTE` (90) limits each person.
**Mirror channels (Nov 2026).** Settings › Telegram takes up to three extra channels (`mirrors` in `telegram.json`; `SUD_CHANNEL` of the bot is a comma separated list, main first). A backup is written to EVERY channel, each with its OWN chain (own manifest, own pinned message, own pieces, own salt and so own key and bucket ids): a file id of one channel means nothing in another, and a banned channel takes its files with it, so the mirror cannot just point at the main channel's files. `runBackupAll` brings the channels up to date one after another; a channel that fails does not stop the others (a banned main channel is exactly when the mirror matters) and the result says which worked («Qisman: 1/2 …», `last_backup.channels`). Reads fall back in order: the catalog and the locator (`readRemoteCatalog`), a load and a restore (`withFallback`: a failed attempt is reported in the next one's message, so using a mirror is never silent); a wrong passphrase stops at once (it is wrong for every chain). The bot does the same: `sync` tries the channels in order (a banned channel, a deleted manifest message or a deleted index piece moves it on), `bucket_text` asks the next channel for a bucket whose piece has vanished, `/health` reports `channel` / `channels` / `degraded` and `/status` says «asosiy kanal ishlamayapti», and once on a mirror an unchanged pin downloads nothing. **Limits that stay:** the mirror protects against a banned or emptied CHANNEL and a deleted message or file; it does NOT protect against replacing the BOT: Telegram file ids belong to the bot that received them and a bot cannot read a channel's history, so a NEW bot (made again in @BotFather) cannot read any channel's old files. Revoking the TOKEN in @BotFather (`/revoke`: a new token for the SAME bot) is safe: put the new token in Settings › Telegram and in the bot's `BOT_TOKEN`. Keep Settings › Baza › download as the copy that does not depend on the bot. The bot must be an admin of each channel. Tests: `lib/__tests__/backup.test.ts` › «mirror channels» (a multi-channel fake Bot API), `bot/src/tests.rs` › `mirrors`.
**Mini App design system (Nov 2026, navy).** The Mini App wears the app's «Moviy» (navy) look: the same hues (canvas `#eef0fa`, navy `#1a2350` accent, brand blue `#3b5bdb`, green and rose only for done/paid and overdue; the dark theme reverses the ramp), and the logo (the four-segment ring, drawn from tokens so it follows the theme) on a navy tile in the header. **Company names and sides (Nov 2026).** The bot used to know a company only by its STIR. The name comes from the company's OWN bills: the most common `payer` among the bills whose `payer_tin` is the company (`companyNameOf`, the courts' spelling, Cyrillic or Latin), written into the manifest as `companies[tin].name` at every backup (a backup now starts from the channel's previous `companies` map, so a company another computer scraped keeps its name and dates; the catalog carries the name too). Without a recorded name the bot LEARNS it (`party::learn_name`): the party text that is in at least 60 % of the company's hearings (at least three), because every case was found by the company's TIN. Hearings rows, `/hearings`, the case screen (the company's side is outlined and marked «siz», a line says «<name> — Javobgar · qarshi tomon: X») and `/case` use it; bills show who paid (`Toʻlovchi`). **A backup never takes data away from the channel (found on the second company, Nov 2026).** A manifest used to list only the buckets of the computer that made it, so a backup from a database holding ONE company (207275139) dropped the other (ANOR BANK) from the pinned view, and the bot lost it. Now a backup starts from the UNION of the channel's history: `chainBuckets` walks the manifests (`prev` pointers, up to 60) and takes the newest version of every bucket by name. A bucket this computer has nothing for is carried over unchanged; a bucket both have is MERGED (`mergeBucketText`: every row of either; a row in both is the newer one by its own time, bills without a time: the local copy; the locator and state lines by key), and only a merge that changed something is uploaded. So a laptop and a second machine can both back up and the channel holds everything; the price is that a deletion on one computer does not propagate (nothing is ever deleted from the channel anyway). **Billing load retries.** A page that fails on billing's captcha is retried 8 times (30 s × attempt, about 15 min) instead of 3: on a 123 255-bill company pages 11+ rejected a SOLVED captcha («Failed captcha check») for minutes while other pages passed. The Gemini key also hit 503 (overload) and 429 (quota): save two models of the same key (`gemini` preset + a `custom` entry with another model) and the pool fails over.

**Why a bank's bills are not all there (207275139, Nov 2026).** Billing's search takes only `inn`, `page`, `size` and a captcha token (the official site sends nothing else: no date, status or court filter), and its order is unstable, so a company's bills can only be read by paging. Measured: 123 255 rows (`totalElements`, which counts the repeated «join» rows, so it is NOT the number of distinct bills: one 20 000-row page held 19 604 distinct), 106 171 distinct stored after one and a half passes, i.e. about 12 % still missing; a pass reads a different slice of the order each time, so the union grows slowly. Also measured: a 9 000-10 000 row page at an offset above ~100 000 is rejected («Failed captcha check») again and again while 100-row pages at offsets 110 000-123 000 pass at once, and 60 000+ row pages are always rejected. Therefore: (1) a page that fails 3 times is asked as 5 smaller requests of the same window (`SPLIT`, sizes divide by 5); (2) eight passes with eight page sizes before the load says it is not certain; (3) the bills are only ONE source of case numbers: about 30 % of the stored bills name no case, a bank is mostly billed for postal costs (102 042 «pochta» against 3 995 «davlat boji» bills: the state duty is recovered from the defendant), and cases where the company is the DEFENDANT pay nothing through billing, so they are seen only through the capped TIN lists (100 / 200 rows). More sources for case numbers are an open question (see the owner's note on missing cases).

**Only bills with a case are kept (owner's decision, Nov 2026).** A bill that names no case number is of no use here, so the load stores only bills with a case; migration v5 deleted the old ones (about 30 % of a bank's bills); backups, bucket imports, the locator and the merge of bucket copies drop such rows too (an older backup in the channel still holds them; the next backup merges them away). Because the database can no longer tell a repeated bill that has no case, the load keeps the numbers of the current pass in memory to measure the order's instability, and a pass resumed in another process is never called stable (one more pass follows). Each finished pass is logged (`meta.bills_passes:<tin>`: rows, new bills, repeats) and the status shows a capture-recapture estimate of coverage (`estimateCoverage`: N ≈ known × seen / (seen − new)). Since a case is seen through ANY of its bills (1.4 bills per case on average), coverage of CASES is higher than coverage of bills. A window that needed a split starts every deeper window split (`splitFrom`), which saves three failed full-size attempts (minutes each) per window.
**Which bills belong to a case (Nov 2026, `core/bill-link`).** The gate of the pipeline («only bills with a case are kept») is an explicit decision, not «the field is empty»: `linkOfBill` returns `case` (`claimCaseNumber` is a number), `text` (the field is empty but the description or purpose holds a case number, which is then taken: «… санадаги 4-1001-2129/44390-сонли ҳал қилув қарори»), `claim-cost` (postal / court-payment / video-conference cost paid when a claim was filed: no ruling date, `isInFavor` not false) or `unlinked`; the last two are not kept but COUNTED per pass (`PassLog.links`, shown in the panel: «Ish raqamisiz kvitansiyalar saqlanmaydi: N daʼvo xarajati, M boshqa»). Measured on 2 600 real bills of a water utility: 436 name a case; of the 2 164 that do not, 1 814 are «Почта харажатлари», 226 «Суд тўловлар», 5 video; all have `isInFavor: true` and no `decisionDate`, and none has a sibling bill (same court and payer) within ten minutes, so no rule can tie them to a case, and a guessed link would put a wrong case on a person's file: they stay out. `toBillRow` and `extractBillCases` both use it, so what is stored and what the court is asked about can never disagree.
**Refreshing open cases only (Nov 2026).** After the first full fill (a company with 80 000 cases takes about two days at 2.6 s per case) a refresh must not repeat it: most cases are concluded and never change. `POST /api/bill-cases?tin=…&action=start&refresh=open` (button «Tugallanmagan ishlarni yangilash») runs ONLY a refresh phase instead of a load and a fill: `openFoundQueue` (small columns of `found_cases`, once per job) keeps the cases whose status is not concluded (`isConcludedStatus`: finished, archived, refused stay out; ongoing, unknown and no status go in) and that were last fetched more than 6 hours ago, the longest unrefreshed first; each is asked again (same pacing, back-off and pause as the fill), the stored detail and row are replaced, and a different status, hearing or result counts as `changed` (also announced as an event). A case the court no longer answers for keeps its stored row and is NOT marked tried; a refreshed case gets a newer `t`, so a second run has nothing left to ask. Nothing starts by itself. Tests: `lib/__tests__/bill-cases.test.ts` › «refresh of open cases».
**How to get more out of billing:** (1) keep the page small where it fails (done) and big where it works (pass 0 at 10 000); (2) judge convergence by NEW CASE-BEARING bills per pass, not by `totalElements` (it counts repeated join rows); (3) never parallelise sessions (the site's firewall and captcha scoring punish bursts: failures clustered after ~100 000 rows read); (4) two captcha readers of one key plus failover; (5) a refresh later reads the passes again and only adds; (6) the bills are one source of case numbers; the TIN lists (capped) are the only other one.

## Kuzatuv: the app tells you what is new (`core/watch`, `lib/watch`, `lib/watch-store`)

**What it is.** An opt-in scheduler INSIDE the app (not the Render bot, which never scrapes). Every `intervalHours` (default 6) it re-reads each watched company's economic, civil and administrative court lists and sends Telegram messages with the backup bot's token to the recipients' Telegram ids. Setting: Settings › Telegram › «Kuzatuv (avtomatik)»; stored in `meta.watch_config`; default OFF. The timer (`src/instrumentation.ts` → `startWatchScheduler`, 60 s tick, `unref`) does nothing unless `enabled`: this is the only thing in the app that starts by itself, and only because the operator switched it on. It needs the app running (`Sud.bat keep`; the auto-exit of `Sud.bat` would stop it).

**What is news** (`core/watch.diffRow`). A row's signature is `status|result|hearingDate|hearingTime|hearingStage`. Against `watch_seen` (migration v6: per company and case number the signature, the instances last seen and when the detail was last read): a case number never seen = **new** («Sudga yangi ariza topshirildi»); a changed hearing = **hearing**; a changed status word = **status**. A **new instance** (appeal A, cassation C, supervision I) is only visible in the case DETAIL, so a changed row fetches it (`getCaseLean`), and a sweep reads the detail of up to 15 open cases per company per run whose detail is older than 24 h (an appeal does not always change the row). `ins = null` means the detail was never read: the first instance seen is recorded, never announced.

**Silence rules.** The first read of a (company, court) is a BASELINE: remembered, nothing sent (`meta.watch_base:<tin>:<court>`). An incomplete or failed list is an error line, never a baseline and never «everything vanished». Seen state is written only AFTER the message went out: a failed send is retried at the next run, and with no recipient nothing is remembered. At most 15 messages per company per run, then one «yana N ta» note; the rest goes out next run. A company that fails does not stop the others (`runWatch` never throws).

**The message** (`buildMessage`, always Latin script, `ʻ`/`ʼ`): head by kind, «Siz: javobgarsiz / daʼvogarsiz», case number and court, Daʼvogar / Javobgar with names and STIR, «Kuzatuv: <company> (STIR …)», «Holati: … · Muddat: …», «Majlis: …». The side comes from the parties' TINs in the detail (exact), else from the names (`core/classify.samePartyName`; a very short name like «ANOR» is not distinctive enough and gives no side rather than a guess).

**Pace.** list 2.5 s, detail 2.6 s, send 1.1 s between calls; `clearCourtCaseCache(tin)` before every list so a fresh answer is read. Court lists are capped by the site at about 100–200 rows: a company with more cases is watched on its newest rows. **Routes.** `GET/POST /api/settings/watch`, `?action=run` (read now) and `?action=test` are `privileged`. Tests: `core/__tests__/watch.test.ts` (rules and message), `lib/__tests__/watch.test.ts` (runner with faked court, detail and Telegram).

## Mirror catch-up (`backup.runBackup` with a `Donor`)

Audit of the real channels (Nov 2026): both held a complete, readable chain with no missing piece, but the mirror lacked every bucket of one company (the bank) that the main channel had got from another computer: each channel has its OWN chain and a backup only carries forward what that channel's own chain holds, so a mirror started later never learned it. Now `runBackupAll` makes the first channel that worked the **donor** of those after it. In a mirror's run (1) a bucket this computer renders that has FEWER rows than the donor's is merged with the donor's text (`mergeBucketText`); (2) a bucket the donor holds and this chain lacks (or holds with fewer rows) is downloaded from the donor, merged with this chain's own version, sealed with THIS channel's key and sent (`put`); (3) the donor's `companies` (first date, «as of», name) are unioned in. Row counts decide, so once the channels agree nothing is downloaded (a second backup sends only a manifest). A failed main channel is no donor (the mirror backs up from this computer alone, as before); the summary line says «N ta boʻlak asosiy kanaldan koʻchirildi». Limit: the copy goes main → mirrors only (a mirror holding more than the main channel does not feed it back). Tests: `lib/__tests__/backup.test.ts` («CATCH-UP …»).

## Per-person reminders: morning, evening, and where the settings live (`bot/src/prefs.rs`, `digest.rs`)

**What a person can set** (`/settings`, also `/reminders`): the morning time (07:00 / 08:00 / 09:00 / off), the evening time (17:00 to 20:00 / off), how many days the morning message covers (3 / 7 / 14 / 30) and which companies the reminders are about (all, or a chosen few). Defaults: morning 08:00 for 7 days, evening 18:00, all companies. The evening message is TOMORROW's hearings only («🌙 Ertangi majlislar», count and the first time); both are silent when there is nothing to say. Times are Uzbekistan time; each reminder may go out up to an hour after its time (a restart inside the window sends it once), once a person per day (`digest::Sent`, a `tick(sh, now, sent)` that tests drive with a chosen clock).

**Where the settings are kept: a message pinned in the person's own chat.** The bot's host loses its disk on restart and the bot never writes to the backup channel, so the settings screen IS the storage: the FIRST `/settings` sends a message and pins it (later `/settings` send a fresh screen at the bottom of the chat but do NOT pin again: every pin leaves a «pinned a message» line, and the pinned one is only the storage; `settings_reply`), and its last line carries `sozlama kodi: m=0800 e=1800 d=7 c=*`. Every button edits that message in place (a press on an older screen also edits the pinned one) and the cache (`Shared.prefs`). `prefs_of(user)` reads the pinned message back (`getChat`) the first time a person is needed after a start; no pinned settings means the defaults; a Telegram failure means the defaults for now and another try after five minutes. Checked against the real Bot API (Nov 2026): `pinChatMessage` works in a private chat, `getChat` returns the pinned message's plain `text`, and an edit changes it. Limits: unpinning or deleting that message, or pinning another message later, returns the defaults; a person who never talked to the bot has no chat to read. Callbacks are `s:m:0800`, `s:e:off`, `s:d:14`, `s:c:<STIR>`, `s:c:all` (all under Telegram's 64 bytes); `Prefs::apply` accepts only the offered values. Tests: `prefs.rs` (code round trip, button rules, company toggling, the screen) and `tests.rs` › `reminders` (pin, edit, restart read-back, stranger, two people, filters, horizons).

**The guide's reader:** the numbered chips jump to any section; the only other control is one «Keyingi boʻlim» button at the bottom (it scrolls the next section's heading into view), because after a long section the chips are far above. Section 12 of the guide covers `/settings`.

## Bot link: instant ping, `/refresh STIR` from the phone, paged `/stats` and `/settings` (Nov 2026)
**The idea.** The app (the computer) scrapes and writes; the bot (Render) only reads the Telegram backup. The link adds two things and is always OUTBOUND from the computer (no open port, nothing to forward): (1) after every successful backup the app POSTs `/link/synced` and the bot's sync loop wakes at once (`Shared.wake`, a `Notify` that cuts the 5-minute sleep) instead of waiting for its next look; (2) every 60 s the app POSTs `/link/pull` («anything for me?») and gets the STIRs people asked for with `/refresh STIR`.
**Auth.** Both calls carry `x-sud-ts` and `x-sud-sig` = hex `HMAC-SHA256(key, "<ts>\n<path>\n" + body)` with `key = HMAC-SHA256(botToken, "sud-link-v1")`. The token is already on both sides, so there is no new secret; a call more than 2 minutes off, another path or another body is refused with the same 401 (`link.rs`, `lib/bot-link.ts`; the same test vector, computed with Python, is in `bot/src/link.rs` and `lib/__tests__/bot-link.test.ts`: change one side and both tests fail). A captured call can be replayed only inside that window and only does what it did (pull hands out each job once). The app trusts the bot's answer for nothing but a STIR of 9 digits and a whole number id (`parseJobs`).
**The flow of `/refresh`.** `/refresh STIR` → the bot checks the app was seen within 3 minutes (else «Ilova ulanmagan»), dedupes (a second person asking the same STIR joins the first request), caps 3 pending per person and 20 in all, and refuses a company finished less than 5 minutes ago → the app's next pull takes it → ONE company at a time, and not while the bills job or Kuzatuv runs: the three court lists are read fresh (`clearCourtCaseCache`, 2.5 s apart, at least one must be complete), then the open cases found earlier are asked again (`startJob(tin, {refresh: 'open'})`) → `backupNow()` (`lib/auto-backup`: needs the automatic backup on, skips the 15-minute gap, `unchanged` when the channel already has everything) → the app reports `done: [{id, ok, note}]` in `/link/synced` ONLY after a backup that STARTED after the company was read (`BackupView.doneStartedAt >= finishedAt`), so the bot never says «yangilandi» about data the channel does not hold → the bot stores the result, syncs, and only then tells the people (`link::deliver`, called by the sync loop after each look), reading the new counts from its fresh index. A failed read is reported at once with its reason and needs no backup. A request nobody takes for 10 minutes, or takes and never finishes for 30, ends with a «javob bermadi» message instead of silence. The queue is in memory: a bot restart empties it and the person asks again.
**What it does not do.** It never loads bills (that needs the captcha reader and minutes to hours): it is the «Yangilash» of the court lists and the open cases. It does not start by itself: off until Settings › Telegram › «Bot bilan ulanish» is switched on with the bot's https address (plain http only for localhost). The computer must be on (`Sud.bat keep`).
**Paging.** `/stats` without a STIR shows 10 companies a page, biggest first (bills + found), `Oldingi / n/N / Keyingi` redraw the SAME message (`t:<offset>`), and the overview is read only for the page shown. The `/settings` company picker is two to a row, 8 a page (`PICK_PAGE`) with `‹ n/N ›`; every button carries its page (`s:c:<tin>@<page>`, `s:g:<page>@<page>`), so a press redraws where it was, and the screen stays far below Telegram's ~100 buttons and 64-byte callback limits at hundreds of companies (`prefs.rs` tests build 100 companies).

## Kuzatuv messages say what changed, and a flapping list is not announced every run (Nov 2026)
A `status` / `hearing` message used to show only the new status («Holati: Arxivga topshirilgan»), so a case announced again and again looked identical each time. Now the event carries the remembered signature (`prevSig`) and `core/watch.changeLines` writes each difference as «oldin → endi»: `Holati: Koʻrib chiqish jarayonida → Qanoatlantirildi`, `Natija: …`, `Majlis: 12.03 10:00 → 20.03 11:00` (a new date is «(yangi)», a removed one «belgilanmagan»); a change replaces the bare status line. A `new` case shows its filing date, and one filed more than `FRESH_DAYS` (45) ago is headed «Roʻyxatda ish paydo boʻldi» instead of «Sudga yangi ariza topshirildi» (it only appeared in the list now, e.g. a list cut at 100-200 rows). Why it repeated: (1) the same case number twice in one list was judged row by row, so each row differed from the memory and the two were announced and remembered in turn, every run; now a number is ONE case (news only if no row of it matches the memory); (2) a status written in another script, case, apostrophe or spacing (a list read from another source) was a different signature; `diffRow` now compares `normSig` (Cyrillic→Latin, lower case, one apostrophe, one space) and the stored signature is NOT rewritten, so nothing floods after the update; (3) whatever else makes a list flap between two answers: `watch-store.transitionAnnounced/rememberTransition` keep the last 8 announced changes of a case (`meta` key `watch_tr:<tin>:<num>`, 3 days), and the same change is remembered but not sent again, so a flapping case costs two messages, not one per run. Tests: `core/__tests__/watch.test.ts` › «what changed», `lib/__tests__/watch.test.ts`.

## Reminders are sent once even across restarts (Nov 2026)
The bot's «sent today» memory (`digest::Sent`) was in RAM, and Render's free host restarts and sleeps: a wake-up inside the hour after the chosen time (the window that makes a late restart still send) found an empty memory and sent the same morning/evening reminder again (18:00 and 18:40 in the field). The day last sent is now ALSO part of the person's pinned settings code (`sm=` morning, `se=` evening, `Prefs.sent_m/sent_e`, written by `chat::persist_sent` right after a reminder went out and read back with the other settings; a button press never touches it). `digest::tick` uses the larger of the two memories. A person who never opened `/settings` gets the settings screen pinned the first time a reminder goes out (that is where the marker lives). Tests: `tests.rs` › `a_restart_or_wake_up_inside_the_hour_does_not_send_the_same_reminder_again`.

## Court orders in the bot (`orders:<yy>`, `pdf:<id>`, `bot/src/orders.rs`) (Nov 2026)
**Why this shape.** public.sud.uz refuses scripts, so the bot never goes there; the orders the operator downloaded in the app (one captcha each, ever) travel in the encrypted backup, and the bot only reads them. **App** (`lib/orders-buckets`): two new bucket kinds, rendered from the orders folder (not from the database snapshot) and added to the same loop of `runBackup`: `orders:<yy>` = one line per DOWNLOADED order (`[id, case, instance, result, court, judge, category, pdf id, file name, size, court type, saved at]`, by the case's registration year, so a year's bucket is small and a new order changes one bucket), and `pdf:<pdf id>` = the PDF bytes as they are (content-addressed: sent once, reused afterwards; a published order never changes, so `mergeBucketText` returns the local bytes). EVERY found order has a record (saved at 0 = found, PDF never downloaded: the bot lists it as «yuklanmagan» with no button; an older backup's lines have saved at > 0 only and read the same), and a checked case with no order and no failed attempt has a line `["k", case, checked at]` so the bot can say «tekshirilgan, qaror eʼlon qilinmagan» instead of «unknown»; only a downloaded order has its `pdf:` file, and a PDF with no record has no case to belong to and stays on the computer. In a merge the copy that HAS the PDF wins (a computer without the file never turns the channel's «downloaded» back), and the later check replaces an earlier one. `ordersFingerprint()` (names and sizes of `files/*.pdf` and `shards/*.jsonl`, no file read) is part of the auto-backup fingerprint, so a newly imported HAR or downloaded order starts the next automatic backup and the link pings the bot. Restore and «load company» ignore both kinds (`importBucket` returns 0): they are for the bot; the PDFs are also on the monoblock and the metadata has its own protected copy. **One case, many instances:** a case number has an order per instance (first, appeal, cassation, repeated cassation, taftish) and sometimes several in one instance; each is its own record keyed by the order id and its own PDF, never merged by case number. The bot lists them first instance first, and names a repeated instance «Apellyatsiya 1», «Apellyatsiya 2». **Bot:** `/orders <case or STIR>` (and the case card's «Qarorlar (n)» button, callback `r:<case>`) lists them with one button per PDF (`o:<pdf id>`, ≤ 64 bytes); a press opens `pdf:<id>` through the usual `bucket_text` (piece hash, authentication tag and keyed id are checked), and sends it with `sendDocument` (multipart written by hand: `telegram::multipart_document`, tested byte for byte), nothing touches the host's disk. A damaged or missing piece is never sent; the person is told. The year of a case number is its third segment's first two digits (`orders::year_of` = the app's `registeredKey / 100`), so a case reads ONE bucket. Not done: asking the app to download one not-yet-downloaded order from the phone (a «Yuklash» button through the link: the download often needs a person's captcha), the Mini App tab, and restoring PDFs to a new computer. Tests: `lib/__tests__/backup.test.ts` › «downloaded court orders», `bot/src/orders.rs`, `tests.rs` › `orders`.
